# 分析レシピ — 集計の定義と限界

Bamboo の REST API に集計専用のエンドポイントはない。成功率や所要時間の推移は、結果履歴をページングで取得し、取得側で計算する。このファイルはその定義を固定し、レポート間で数字の意味がずれないようにするためのもの。

## 基本の取得

- 対象プランの結果履歴を `GET /rest/api/latest/result/{planKey}` で新しい順に取得する（ヘルパーの `history` / `results`）。
- 既定の窓は 90 日。窓は `buildCompletedTime`（無ければ `buildStartedTime`）で判定する。
- 取得上限（ページ数）に達したら打ち切りとして記録し、「取得できた範囲での集計」であることを明記する。

## 指標の定義

| 指標 | 定義 |
|---|---|
| 実行回数 | 窓内の Finished な結果の件数（進行中・未完了は数えない） |
| 成功率 | Successful の件数 ÷ 実行回数。Failed と Unknown は分母に入れ、分子に入れない |
| 所要時間 | `buildCompletedTime − buildStartedTime`（秒）。取れない結果は件数から除外し、除外件数を durationSeconds.count と総数の差で示す |
| 所要時間の代表値 | 平均だけでなく中央値と p95 を出す。p95 は nearest-rank |
| 連続失敗 | 最新の Finished 結果から遡って Failed が続く件数 |
| 最終成功日 | 窓内で最も新しい Successful の完了時刻 |
| 長期未実行 | 窓内に Finished が 0 件、または最終実行が窓の開始より前 |

## 傾向の見方（基本形）

1. プラン単位: 成功率と連続失敗で「壊れたまま放置」を抽出する。最終成功日と合わせて「いつから成功していないか」を言う。
2. 所要時間: 中央値と p95 の差が大きいプランは、時々極端に遅い実行がある。結果詳細のステージ／ジョブ結果で、どのステージが時間を食っているかを確認する。
3. 活動量: 実行回数が窓内で 0 のプランは、無効化プランと合わせて「移行しない候補」「棚卸し対象」として分ける。
4. ブランチ: ブランチ数と直近のブランチ実行の有無で、ブランチ運用の規模感を見る。
5. デプロイ: 環境ごとに結果履歴を数え、回数・成功率・直近のデプロイ日時を並べる。現行バージョンは履歴の先頭である。

## 限界（レポートに必ず添える）

- Expiry で削除された古い結果は戻らない。窓を長く取っても、残っている履歴以上には遡れない。
- 見える範囲は認証ユーザーの権限の範囲だけである。全社集計ではない。
- ビルドログ全文の API はない。失敗原因の特定は結果詳細（ステージ／ジョブ、テスト集計）までで、ログ本文が必要なら Web 画面で確認する。
- 所要時間はキュー待ちを含まない（開始から完了）。待ち時間の分析は結果のメタデータに依存し、このレシピの範囲外。
- サンプルが少ないプラン（実行回数が一桁）では成功率や p95 の意味が薄い。件数を必ず併記し、断定を避ける。
